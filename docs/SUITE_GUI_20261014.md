## 1. Suite GUI — cosa è implementato

- Tk solo stdlib, importato solo dentro `SuiteApp` (`tools/psvr_suite/app.py`).
  Headless (`--headless-check`) valida import reali + schema canonico senza
  Tk/hardware e rifiuta se `tkinter` è già importato.
- Schema canonico backend strict, ordine stabile (`CANONICAL_KEYS`, 27 chiavi):
  `tracking_mode`, `fallback_3dof`, `reacquire_blend_ms`, `reacquire_speed_m_s`,
  `initial_offset_m`, `head_offset_model_m`, `position_scale`, `position_filter`,
  `min_cutoff_hz`, `beta`, `min_area`, `value_min`, `saturation_min`,
  `opening_size`, `exposure`, `gain`, `fps`, `width`, `height`,
  `intrinsicsPath`, `rigPath`, `imu_rig`, `optics_profile`,
  `tracking_config_path`, `imu_calibration_ms`, `imu_stale_ms`,
  `imu_max_gap_us`.
  Validazione in `settings.validate_preferences`: chiavi ignote/mancanti,
  NaN/inf e fuori-range alzano `ValueError`; nessun autocorrect/clamp.
- Default live verificati (`settings.default_preferences`, confermati anche da
  `headless_check`): `6dof`, `fallback_3dof=true`, `150 ms / 1,5 m/s`,
  `one_euro 2,5 Hz / β8`, camera `640×480@75`, `exposure 13 / gain 0`,
  `min_area 6 / value_min 60 / saturation_min 90 / opening_size 0`,
  intrinseci `pseye_blue_640x480_calibrated.json`, rig
  `psvr_front_leds_refined_20261011.json`, `imu_rig`
  `psvr_nine_leds_refined_sides_20261011.json`, `optics_profile=current`,
  `tracking_config_path=config.json`, IMU `8000 / 100 / 5000`.
  Il vincolo preset utente accettato **60/6/13/0** è distinto e indica solo
  `value_min 60 / min_area 6 / exposure 13 / gain 0` LED-track
  (cfr. `configurations/pseye_led_capture_reference.json`,
  `tools/psvr_camera/README.md`); non confonderlo con l'intero
  `default_preferences` (che include anche `saturation_min/opening/fps/...`).
- `AppModel` (puro, senza Tk/camera/hardware): parsing tipato widget-string
  + validazione strict backend. Modi `3dof/6dof`; filtri
  `one_euro/kalman_initial/kalman_optimized`; profili ottici
  `current/identity/mild/medium/peripheral/stronger`.
- Chiamate bloccanti su worker seriale, mai sul main Tk; eventi display in coda
  con throttle; poll stato ogni 2 s senza overlap (compatibile con cal 8 s).
  Campi mancanti da backend `status()` → `sconosciuto`, mai inventati.
  `Runtime.status()['driver_tracking']` è autoritativo per modo/fallback/
  recovery; la stima worker non è fidata quando l'IMU non è valida.
- File utente SOLO `configurations/psvr_suite_user.json` su salvataggio
  esplicito (`save_preferences` atomica + `.bak` locale); baseline mai
  riscritte. Senza file utente si leggono live driver prefs via
  `preferences_from_driver()` se esposto, altrimenti i default.
  Rifiuto esplicito di sovrascrivere la baseline IMU globale `config.json`.
- Lock singleton OS-held, crash-safe (`msvcrt`/`flock`): GUI (`app.py`
  `SuiteLock` + `LOCK_REL=logs/psvr_suite.lock`, acquisito in `main()` con
  rifiuto seconda istanza) e ownership runtime (`runtime.py` `SuiteLock`
  default `logs/suite.lock`, usato da `RuntimeController`).
  Chiusura rilascia `runtime.close()` + `tracking.stop()`
  posseduti, senza fermare SteamVR esterno (solo Stop esplicito).
- Avvio (`run_suite.ps1` → `.venv-camera/Scripts/python.exe -m tools.psvr_suite`):
  `--start-vr` (VR dopo init, runtime poi tracking con guardia),
  `--attach` (solo tracking verso VR esistente, nessun cambio modo hardware;
  `--attach` + `--start-vr` incompatibili, vince attach),
  `--check` → `--headless-check`, `--tab Sessione/Tracking/Camera/Posizione/
  Ottica/Diagnostica`.
- `RuntimeController` (`runtime.py`): unico owner lifecycle; USB a
  `psvr_diag.exe`, pose/HMD a `psvr_runtime_probe.exe`; mai kill arbitrari —
  solo handle propri, stop runtime solo via URI graziosa `vrmonitor://quit`
  con wait bounded 25 s. `start_vr` idempotente: se `vrserver/vrcompositor`
  già attivi non li chiude; da fermo esegue `--vr-mode` poi `--leds-on`
  PRIMA del launch, attesa `vrserver` 30 s, finestra calibrazione guidata
  8 s DOPO `vrstartup`, poi probe readiness 500 ms (pose IMU valide osservate,
  mai inferite; senza pose va in `vr-awaiting-tracking`, non deadlock).
  `to_cinema` chiude runtime poi `--cinema-mode` con conferma F0.
  `recenter`/`recalibrate` solo su HMD verificato `PSVRPC-HMD-0`
  (queued/dispatched osservati, mai “applicato” presunto).
  `show_grid` worker bounded con path griglia assoluta + log unico assoluto;
  readiness non gated su pose (sicuro anche in 3dof).
  `apply_driver` ferma runtime, applica sole chiavi owned, riavvia solo se
  girava già (override `restart` esplicito possibile).
- `TrackingWorker` (`tracking.py`): riusa SOLO import accettati
  `tools.psvr_camera` (blue LEDs, intrinseci, `DriverImuSource` su 4272,
  `ImuLedTracker` PnP standard, `PositionPipeline` esclusivo, sender
  `psvr.position` v2 su 4271). Mai `DiagnosticHID`/avvii standalone.
  Preview senza driver: solo detector RGB, nessuna posa inventata.
  Sender UDP solo se `tracking_mode==6dof` E IMU driver realmente bound;
  nessuna sessione inventata. Nessun filtro orientamento; offset testa via
  modulo esistente; thread mai Tk.
- `setup_trial.py`: abilita policy richieste via store selettivo; default
  `--optics peripheral`; rifiuta se `configurations/psvr_suite_user.json`
  esiste già (apply dalla suite invece); `lens_acceptance_verified=false`.
- `deploy.py`: backup pre-integrazione driver/probe con manifest + sha256;
  rifiuta se `vrserver/vrcompositor` attivi; `--backup-dir` deve essere nuova
  in parent esistente.

## 2. Fallback ottico 3DoF e recovery — comportamento verificato nel codice

Chiavi driver owned (`settings.OWNED_KEYS`, sezione `driver_psvrpc`):

- `positionEnabled` (= `tracking_mode==6dof`), `imuExportEnabled=true`,
  `positionFallback3DofEnabled` (opzionale: omessa = default driver false,
  solo se fallback abilitato), `positionReacquireBlendMs`,
  `positionReacquireMaxSpeedMps`, `positionInitialOffsetX/Y/Z`,
  `imuCalibrationMs`, `imuStaleTimeoutMs`, `imuMaxSampleGapUs`.
- Ottica separata (`OPTICS_KEYS`): `distortionMode`, `distortionProfilePath`,
  scritte SOLO con `apply_optics=true`.

Controller puro `driver/position_continuity.hpp`:

- Default `fallback_3dof_enabled=false`, `reacquire_blend_ms=150`,
  `reacquire_max_speed_mps=1,5`; validazione `0..2000 ms`, `0,01..10 m/s`,
  offset `±10 m` finiti.
- `preview()` non muta timer/storia; `update()` solo da RunFrame/publish.
  Validità ottica fornita separatamente; affidabilità pacchetti/origine/epoch
  resta di `PositionBridge`; mai ingerisce/genera pacchetti ottici.
- Senza `fallback_3dof`: policy legacy strict invariata (`sixdof` o
  `position_grace`, mai fallback implicito).
- Con opt-in attivo e misura assente: azzera `has_position`, tiene
  `published_` se stessa sessione/epoch altrimenti `initial_offset`,
  `position_fallback_3dof=true`, `tracking_mode=fallback_3dof`; ignora
  esplicitamente la grace translation.
- Al ritorno misura su stessa sessione dopo degrado: prima publish con
  continuità esatta (`out.position=published_`, `reacquiring`), poi blend con
  `duration=max(blend_ms, 1000*|correzione|/max_speed)` e decay a rate
  costante; solo lo speed dell’offset correzione è limitato, il target ottico
  in movimento è seguito senza clamp finto né lag aggiunto.
  `blend_ms=0` = blend disabilitato esplicito. `recovery_offset/remaining/
  duration/elapsed` esposti. Cambio sessione/epoch, clock regresso,
  incoerenza o display/orientamento non fresco → reset/invalid, mai mix epoch.

Contratto posa (`driver/pose_bridge.hpp` + `pose_transition_trace.hpp`):

- Nomi wire: `3dof`, `6dof`, `position_grace`, `3dof_fallback`,
  `6dof_reacquiring`, `invalid`.
- `driver_pose`: senza `position_enabled` resta contratto 3DoF
  (posizione zero, salvo offset iniziale esplicito). Con 6DoF opt-in,
  orientamento solo non basta: posizione mancante/stale/rifiutata/incoerente
  = `Running_OutOfRange` esplicito, mai zero sintetico. Hold last-good solo
  se autorizzato dal controller; `poseTimeOffset` usa età IMU, non età
  translation held. Diagnostica `sensor_tick_gap` preserva FIRST cause su gap
  fusion (`record_failure`).
- `Runtime._driver_tracking()` mappa `mode/orientation_valid/position_valid/
  pose_valid` + `position_m/session_id/recenter_epoch/imu_sample_age_ms/
  recovery_*` e deriva `fallback_active=(mode==3dof_fallback)`,
  `recovery=(mode==6dof_reacquiring)`; campi ignoti restano `None`, mai finti.

Smoke reale (`tools/psvr_suite/hardware_smoke.py`,
schema `psvr.suite.real_static_smoke`, `lens_acceptance_verified=false`):

- Sospende pubblicazione ottica reale (mai pose inventate):
  `optical_fix` 2 s → `tracking_mode=3dof` 0,4 s → `optical_publication_paused`
  2 s → ripristino prefs → `optical_fix_recovered` 3 s.
  `positionEnabled` driver resta TRUE, orientamento resta live.
- Check: `real_6dof_before` (≥1 `6dof` + `position_valid`),
  `fallback_valid_without_optical_fix` (tutti `3dof_fallback` +
  `pose_valid` + `orientation_valid` + `position_valid is False`),
  `returned_to_6dof`, `pose_valid_through_recovery`.

  (valori o assenza da `before`/`before_absent`); rifiuta se `schema` estraneo,
  journal mai applicato, altro file settings, `after` non più corrispondente
  (lavoro successivo cambiato), o hash preserved sezione diverso (chiavi non
  owned mosse). Ritorna `psvr.suite.driver_rollback` con `restored_keys`.
- Backup suite: `logs/suite_settings_before_20261014/settings_before.json` +
  `journal.json` (stesso schema sopra). Backup install:
  `logs/suite_install_before_20261014/` (`driver_psvrpc.dll` sha256
  `284ECF...3ADE`, `psvr_runtime_probe.exe` sha256 `4639E4...94BA`,
  `manifest.json` schema `psvr.suite.install_backup`).
- Comandi (SteamVR CHIUSO; directory `NEW_*` nuova, mai overwrite; rifiutano
  journal stale per preservare lavoro successivo):
